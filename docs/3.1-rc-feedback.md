### Findings

**R1-1: the errors table names a field by its ref, not its label.** Not new in 3.1. In the
grouped case the table reads `Row 3 · items.1.sku · SKU is required`. The row is now right, but
`items.1.sku` is the engine's address for "the second item's SKU". The table has always shown
`problem.ref` (`import-errors.component.ts`), so a flat config shows `personal.firstName` the
same way in 3.0. Suggested: show the field's label, with the item number for a collected item
("Item 2 / SKU"), and keep the ref in a tooltip. Not a blocker: the message names the field
("SKU is required"), and the row is right. Proposed for 3.1.0 or 3.2, owner decides.

**R1-2: the published 3.0.0 server cannot share an install with a 3.1 prerelease core.**
Expected, not a defect. `@dynamic-entity/server@3.0.0` peers on `@dynamic-entity/core@^3.0.0`,
and npm does not let `^3.0.0` match `3.1.0-rc.1`, so the round installed it in a project of its
own. A real app upgrades core and server together, as MIGRATING-3.1 says. At `3.1.0` the range
matches and this goes away.

**Observations**
- The capability refusal reads the same for a 3.1 server without grouping and for a 3.0.0
  server, by design: both lack the `"group"` feature, and the fix is the same.
- The harness itself read workbooks in Node without `exceljs` at first. sheet-to-schema 1.3 said so
  exactly (`PEER_MISSING`, "run `npm install exceljs`"), as designed.
