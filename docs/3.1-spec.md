# Dynamic Entity 3.1 Spec — Browser xlsx, Server Grouping, Transport Checks

Oct 18, 2026 · @Nizamudeen S

## Purpose and scope

Dynamic Entity 3.1 brings sheet-to-schema 1.1 into DE: xlsx in the browser wizard, grouping on DE's server (opt-in), and the server-capability check in `HttpImportTransport`. Every change is additive; 3.1 is a minor release.

**Baseline:** DE 3.0.0 (four packages, `latest`), depending on `sheet-to-schema ^1.0.0`, which now resolves to 1.1.0 with all DE suites green (drift run 39121166216). Today the wizard's default parser reads only `.csv`, `.tsv` and `.txt`, chosen by file extension; xlsx in the browser needs the app to register the ExcelJS parser from EXTENDING. DE's server refuses grouped plans, and a DE test pins that refusal.

**In scope**

- A: the wizard reads CSV through sheet-to-schema's `readCsvFile` by default, and CSV and xlsx through `readSheetFile` with the opt-in `ngx-dynamic-entity/xlsx` entry. Both decide the format from the file's bytes.
- B: DE's server can import grouped plans, behind an option that is off by default, after DE's form adapter is tested with server-side grouping.
- C: `HttpImportTransport` checks a grouped plan against the server's advertised `features`; the wizard shows the new errors clearly.
- DE depends on `sheet-to-schema ^1.2.0`.

**Non-goals**

- A wizard screen for building grouped plans (Phase 4, the Angular mapper). In 3.1, grouped plans come from code.
- Turning server grouping on by default (DE 4.0, Open questions).
- Positional arrays in DE (decision 5 stands: compact-only).
- Storing moved containers once (decision 9 stands: dual write kept).

## Step 0: how bundlers treat the optional ExcelJS import

Before any 3.1 code, find out whether an Angular app that does not install `exceljs` still builds when it imports `sheet-to-schema/browser`. The answer decides Feature A's shape.

**Why it matters.** `readSheetFile` loads ExcelJS with a dynamic `import('exceljs')`. Bundlers resolve dynamic imports at build time. The 1.1 rounds proved the lazy chunk works when `exceljs` is installed, but every bundled test app had it installed. If Angular's builder fails on an unresolvable `exceljs`, making `readSheetFile` the wizard's default would break the build of every DE app that never reads xlsx.

**The check.** A fresh Angular 21 app (application builder) that imports `readSheetFile`, with `exceljs` not installed: run `ng build` and `ng serve`. Repeat with Vite and webpack for completeness. Record: does it build, and does reading a CSV work at run time?

**Outcomes**

| Result | Feature A becomes | Also needed |
| --- | --- | --- |
| Builds without `exceljs`; CSV works; xlsx gives the install message | `readSheetFile` is the wizard's default parser | Nothing in sheet-to-schema |
| Fails to build without `exceljs` | Default stays CSV-only; xlsx is an opt-in secondary entry, `ngx-dynamic-entity/xlsx` | A sheet-to-schema 1.1.1 that gives CSV-only users a module with no `exceljs` import at all, or documents the build requirement |

The check runs once, in a scratch app, and its result is written into this spec before Feature A starts. Nothing is assumed.

### Result (Oct 18, 2026)

**Neither row holds as written.** With Angular's application builder, `ng build` fails without `exceljs`, which is the second row. `ng serve` builds and runs, though, so a developer finds out only when the production build breaks. Where a bundler does let the app through (Vite, or an app that marks `exceljs` external), the xlsx error is not sheet-to-schema's install message, except under webpack's `IgnorePlugin`. In every setup, reading a CSV works.

**Setup.** Scratch apps outside both repos, with sheet-to-schema 1.1.0 and exceljs 4.4.0 from npm, on Node 24.19.0 and Windows 11:

- A fresh Angular 21.2 app (`@angular/build:application` 21.2.27, zoneless) that imports `readSheetFile` from its root component.
- A plain ES module app built with Vite 8.3.4 and with webpack 5.112.0.

Each app reads `case3_excel_semicolon.csv` and then `case1_1904_dates.xlsx` from sheet-to-schema's fixtures, in Chromium 156.0.8078.4, Firefox 157.0 and WebKit 27.2 (Playwright 1.64.1).

**Without `exceljs`: does it build?**

| Bundler | Builds? | Exact error |
| --- | --- | --- |
| Angular, `ng build` | **No** | `X [ERROR] Could not resolve "exceljs"` at `node_modules/sheet-to-schema/dist/browser/index.mjs:470:115` (`await import('exceljs')`), with esbuild's hint to mark it external or add `.catch()` |
| Angular, `ng serve` | Yes | (the dev server pre-bundles `node_modules` with Vite, which stubs the missing optional peer) |
| Angular, `ng build` with `externalDependencies: ["exceljs"]` | Yes | — |
| Vite, `vite build` and `vite` (dev) | Yes | (Vite replaces an unresolved optional peer with a stub module that throws) |
| webpack, plain | **No** | `Module not found: Error: Can't resolve 'exceljs' in '…/node_modules/sheet-to-schema/dist/browser'` (at `index.mjs 462:108-125`) |

| webpack with `IgnorePlugin({ resourceRegExp: /^exceljs$/ })` | Yes | — |
| webpack with `resolve.alias: { exceljs: false }` | Yes | — |

**Without `exceljs`: what reading does.** The CSV read as `csv`, with delimiter `;` and 2 rows, in every setup that built, in all three browsers. The xlsx threw:

| Setup | Chromium | Firefox | WebKit |
| --- | --- | --- | --- |
| Vite build and dev; Angular `ng serve` | `Error`: `Could not resolve "exceljs" imported by "sheet-to-schema". Is it installed?` | same | same |
| Angular `externalDependencies`; webpack `externals` | `TypeError`: `Failed to resolve module specifier 'exceljs'` | `TypeError`: `The specifier “exceljs” was a bare specifier, but was not remapped to anything. Relative module specifiers must start with “./”, “../” or “/”.` | `TypeError`: `Module name, 'exceljs' does not resolve to a valid URL.` |
| webpack `IgnorePlugin` | `Error`: sheet-to-schema's install message (`sheet-to-schema/browser needs the "exceljs" package to read .xlsx files, and it is not installed. …`); `cause` is webpack's `Error: Cannot find module 'exceljs'` with code `MODULE_NOT_FOUND` | same | same |
| webpack `alias: false` | `TypeError`: `o.Workbook is not a constructor` | `TypeError`: `o.Workbook is not a constructor` | `TypeError`: `undefined is not a constructor (evaluating 'new o.Workbook')` |

None of these errors has a `code`. Firefox's message uses curly quotes (U+201C, U+201D).

**With `exceljs`.** All three bundlers build, and in each browser the CSV and the xlsx both read. That covers `ng build`, `ng serve`, `vite build`, `vite` dev and webpack. ExcelJS is only in the lazy chunk: 929 KB under Vite, 944 KB under Angular (217 KB transferred), and webpack's `974.*.js`. Angular warns that `exceljs` is CommonJS ("can cause optimization bailouts").

**With `exceljs`, the chunk fails to download** (the runner aborts the lazy script request). The xlsx then throws:

| Bundler | Chromium | Firefox | WebKit |
| --- | --- | --- | --- |
| Vite, Angular | `TypeError`: `Failed to fetch dynamically imported module: <chunk URL>` | `TypeError`: `error loading dynamically imported module: <chunk URL>` | `TypeError`: `Importing a module script failed.` |
| webpack | `ChunkLoadError`: `Loading chunk 974 failed.\n(error: <chunk URL>)` | same | same |

Vite names its chunk `exceljs.min-<hash>.js`, so a chunk URL can contain "exceljs". A check that matches on the package name alone would report a failed download as "not installed".

**What it points at.** A sheet-to-schema 1.1.1 is needed whichever way Feature A goes:

- It must recognise the missing peer from every error above, not only Node's (Vite's stub message, and the three browsers' unresolved-specifier messages).
- It must give the missing peer a code.
- It must keep a failed chunk download apart from a missing peer.

The Angular build failure decides Feature A's shape. Either DE keeps the default CSV-only and adds the `ngx-dynamic-entity/xlsx` secondary entry, or sheet-to-schema 1.1.1 also ships a module with no `exceljs` import at all.

**Decision (Oct 18, 2026): both.**

- sheet-to-schema 1.2.0 (drafted as 1.1.1) adds `readCsvFile` to its main entry. It is the CSV half of `readSheetFile`, and nothing in its module graph imports `exceljs`.
- DE's default parser uses `readCsvFile`.
- xlsx comes from a secondary entry, `ngx-dynamic-entity/xlsx`, which exports `provideSheetFileParser()` over `readSheetFile`.
- 1.2.0 also gives a missing peer the code `PEER_MISSING`, recognised from every error in the tables above except a failed chunk download, which passes through unchanged.
- 1.2.0 adds a `reason` to `PLAN_GROUP` refusals (Feature C).

Feature A below follows this decision.

## Feature A: CSV and xlsx in the browser wizard

The wizard reads CSV with nothing extra installed. It reads xlsx too when the app opts in. Both go through sheet-to-schema's readers, so browser imports match the server without the app writing a parser.

**The default parser: CSV, over `readCsvFile`.** DE's built-in `defaultSheetParser` becomes a thin wrapper over the `readCsvFile` in sheet-to-schema's main entry (1.2.0). It imports `readCsvFile` from `sheet-to-schema` directly. Core gets no new re-export, because core's re-exports of sheet-to-schema are deprecated for 4.0:

- It calls `readCsvFile(file, { filename: file.name })` and returns `headers`, `rows` and `delimiter`. `LocalImportTransport` then uses `decimalMarkFor(delimiter)` exactly as the server does.
- The format comes from the file's bytes, not its extension. A CSV under another name is read. An `.xlsx` (or any other zip), a legacy `.xls` and a UTF-16 file are refused with `UNSUPPORTED_FORMAT`.
- Nothing it imports asks for `exceljs`. An app that never installs it passes `ng build`, and its bundle holds no ExcelJS.

**xlsx: the secondary entry `ngx-dynamic-entity/xlsx`.** It exports `provideSheetFileParser()`, which registers a `SHEET_PARSER` over `readSheetFile(file, { filename: file.name })` from `sheet-to-schema/browser`:

- It reads CSV and xlsx, deciding the format from the bytes.
- It returns `headers`, `rows` and `delimiter`; `delimiter` is absent for a workbook.
- An app opts in by adding `provideSheetFileParser()` to its providers.
- This entry is the only DE module that imports `sheet-to-schema/browser`, so only an app that imports it needs `exceljs` installed to build.
- An app that registers its own `SHEET_PARSER` instead keeps it, as today.

**ExcelJS.** It is an optional peer of `ngx-dynamic-entity` (`peerDependenciesMeta`), needed only with `ngx-dynamic-entity/xlsx`. Its chunk is 929 KB under Vite and 944 KB under Angular (Step 0), and is fetched only when a workbook is first read.
- If an app imports the xlsx entry without installing `exceljs`, `ng build` fails (Step 0).
- Under a dev server, or with `exceljs` marked external, reading an xlsx fails with sheet-to-schema's `PEER_MISSING` instead, and the wizard shows its install message. Reading a CSV is unaffected.
- A workbook chunk that fails to download is not `PEER_MISSING`, and the wizard does not say "install exceljs" for it.

**Old runtimes.** On a browser without `DecompressionStream('deflate-raw')` (before Chrome/Edge 103, Firefox 113, Safari 16.4), reading an xlsx through the xlsx entry fails with `UNSUPPORTED_RUNTIME`, and the wizard shows its message. The default CSV parser does not need it. The ngx README lists those minimums.

**Documentation.** EXTENDING's hand-written ExcelJS parser is replaced by `provideSheetFileParser()`, with the `readSheetFile` wrapper it is made of for an app that composes its own. DE's documented-parser test runs that wrapper over its fixtures and compares with the server path, so the docs still cannot drift. The ngx README documents the entry, installing `exceljs` for it, and the browser minimums.

## Feature B: grouping on DE's server, opt-in

DE's `createImportRouter` gains `grouping?: boolean`, off by default and passed through to sheet-to-schema's router, but only after DE's form adapter is proven correct with grouped plans on both the browser and the server path.

**Why opt-in.** DE 3.0 servers refuse grouped plans, and a DE test pins it. A 3.1 server that groups by default would change behaviour for anyone upgrading within 3.x, the same reason sheet-to-schema 1.1 made it opt-in. The default can flip in DE 4.0.

**Adapter tests come first.** Grouping has never run through `entityFormConfigAdapter` on the server, and its browser path (`applyMapping` via `LocalImportTransport`) is not covered either. Before the option is added, these must pass through both paths:

| Case | What it proves |
| --- | --- |
| An order config with an `items` array field, one row per item | collected arrays build DE array rows; `_configVersion` stamped once per record |
| The same with the array moved by `refererField` (tab-level) | records use `collectFieldRefs` addresses and the 2.3.1 dual write runs once, on the finished record |
| A required field inside an item; an item with a bad cell | item errors carry their own row, cell and record problems alike (record problems from sheet-to-schema 1.3.0); a bad item fails the whole record |
| A rule that hides a required field in the parent | rules evaluate once on the finished record, with 2.3 precedence |
| A dropdown with a `listName` in an item | lookups resolve per item |
| Parent fields that disagree across a group's rows | one `RECORD_GROUP_CONFLICT` warning, first row kept |
| A stored 2.2 plan with an un-indexed moved-array ref, with a `group` added | `upgradeRefs` still runs before grouping, and the plan is refused: `PLAN_LEGACY_REF` (warning) and `PLAN_GROUP` (error). A plan that groups must be written in v2 form; legacy refs are not rewritten for collected arrays |

Each case runs through `LocalImportTransport` and through DE's router with `grouping: true`, as CSV and as xlsx, and both paths must give identical records, errors, warnings and counts.

**The option.** With `grouping: false` (default), DE's server behaves exactly as 3.0, and its existing refusal test passes unchanged. With `true`, grouped plans import, previews list `features: ["group"]`, and `contiguous: false` is still refused. DE's server README documents the option and recommends `/validate` before a grouped import, since imports are not transactional.

## Feature C: transports and wizard

`HttpImportTransport` checks a grouped plan against what the server advertises before uploading, and the wizard turns every new error into a message the user can act on.

**The capability check.** `HttpImportTransport` switches from `planForServer(plan, planVersions)` to the preview form, `planForServer(plan, preview)`. Outcomes by server:

| Server | Grouped plan | Plan without grouping |
| --- | --- | --- |
| DE 3.1, `grouping: true` (preview lists `"group"`) | sent and imported | sent, as v2 |
| DE 3.1 default, or DE 3.0 (no `features`) | refused before upload: "this server does not import grouped plans; enable grouping on the server or import in the browser" | sent, as v2 |
| DE 2.x (`planVersions` \[1\]) | refused before upload, as today; `refused` includes `group` (it lists every v2-only field the plan uses) | sent, in v1 form |

`LocalImportTransport` already groups through `applyMapping`; 3.1 only adds the tests from Feature B.

**Errors the wizard must show clearly,** each with its own message rather than a generic failure:

- `UNSUPPORTED_RUNTIME`: this browser can't read xlsx files; the minimum versions; CSV still works.
- Missing `exceljs` (`PEER_MISSING`, `details.peer`, from sheet-to-schema 1.2.0): install it to read xlsx files. A workbook chunk that failed to download is not this: it gets the wizard's message for a failed load.
- `UNSUPPORTED_FORMAT`: what the file is (`.xls`, UTF-16, not a workbook) and what to save it as.
- The capability refusal above.
- The server's `PLAN_GROUP` refusals: "grouping is off" and "`contiguous: false` is refused" each get their own message. The wizard tells them apart by the problem's reason (`grouping-disabled` or `non-contiguous`), not by message text; this needs sheet-to-schema 1.2.0.
- `GROUP_NOT_CONTIGUOUS`, `GROUP_TOO_LARGE`, `TOO_MANY_GROUPS`: the key and rows involved (from `ImportFailure.details`), and "sort the sheet by the key columns" where it applies. These come from the server and also from `LocalImportTransport`, where `applyMapping` throws them; the wizard catches them on both paths and shows the same messages.

**The file picker.** Its `accept` list includes `.xlsx` whenever an xlsx-capable parser is active, and only then; a CSV-only setup keeps offering `.csv`, `.tsv` and `.txt`.

## Compatibility and versioning

3.1.0 is a minor release: an app upgrading from 3.0 with no code changes behaves the same, except that the wizard can now read xlsx files.

- **Dependency:** `sheet-to-schema ^1.2.0`:
  - in core and server;
  - in `ngx-dynamic-entity`, directly. Its default parser imports `readCsvFile` from `sheet-to-schema`, and its xlsx entry imports `sheet-to-schema/browser`. It uses the same range as core, so npm installs one copy.

  DE's drift check passes against 1.1.0, and runs against 1.2.0's release candidate on `next` before 1.2.0.
- **Server:** grouping is off unless an app passes `grouping: true`; DE 3.0's refusal test passes unchanged.
- **Browser:** files are now classified by their bytes, not their extension, by the default parser (`readCsvFile`) and by the xlsx entry. A misnamed file that 3.0 refused by name may now be read correctly. A file 3.0 mis-read may now be refused clearly. Without the xlsx entry, an `.xlsx` gets `UNSUPPORTED_FORMAT` with sheet-to-schema's message, where 3.0 gave its own CSV-only message. The CHANGELOG says so.
- **`HttpImportTransport`:** grouped plans now need the server's `"group"` feature. A 3.0 client could send them to any v2 server, where DE 3.0 refused them anyway, so no working setup breaks.
- **Peers:** `exceljs` is an optional peer of `ngx-dynamic-entity`, needed only by an app that imports `ngx-dynamic-entity/xlsx`. An app upgrading from 3.0 without it still builds, because the default parser never imports it.- **Release path:** 3.1.0-rc.1 to `next`, a test round (Round 3's wizard and typings cases plus the Feature B matrix), then 3.1.0. The drift check keeps running throughout.
